# 线程模型与生产实践

Knotra 的核心设计原则之一是**将结构一致性协调与具体的业务执行边界严格分离**。运行时的内部状态机负责维护代际与拓扑，而具体的组件启动、配置校验、动态调用与资源清理则在受控的业务线程上执行。

---

## 五大执行边界规范

为了保证高并发下的系统稳定性，各执行边界的工作范围界定如下：

| 执行边界 | 允许的操作 | 严格禁止的操作 |
|---|---|---|
| **事务回调（`transact`）** | 记录 `provide`、`revoke`、`childContext` 等变更意图。 | 执行 I/O 操作、等待异步结果、调用 Loader 或外部网络。 |
| **Activation 启动（`start`）** | 实例化对象、校验配置、申请资源并登记到 `LifecycleScope`。 | 提前暴露未就绪对象、执行无界耗时阻塞。 |
| **Lifecycle 销毁（`cleanup`）** | 关闭连接池、取消异步任务、释放本地资源。 | 接收新的业务请求、忽略销毁异常。 |
| **动态代理调用（`proxy`）** | 短期业务方法计算、持有短期租约。 | 在租约外启动不受控的后台脱缰任务。 |
| **业务应用线程** | 调用 Capability、带超时等待 Settlement 变更收敛。 | 直接修改或侵入 Knotra 内部状态。 |

## 超时与有界等待原则

在生产环境中，**坚决禁止任何形式的无界等待**：

```java
// 错误示例：无超时预算，一旦发生死锁或外部连接卡死，业务线程将被永久挂起
stage.toCompletableFuture().get(); // 禁止无界 get
```

正确做法是为每一次状态等待显式配置超时预算：

```java
// 1. 等待发布变更收敛
change.awaitSettled(Duration.ofSeconds(10));

// 2. 等待挂载点进入 ACTIVE
handle.requireActive(Duration.ofSeconds(10));

// 3. 等待挂载点自身过渡
ComponentState state = handle.whenSettled()
        .toCompletableFuture()
        .get(10, TimeUnit.SECONDS);
```

**停机等待**：
入门示例中使用 `try-with-resources` 进行语法演示，其内部调用的 `close()` 方法为无界等待。在生产应用停机钩子（Shutdown Hook）中，应使用带超时的异步关闭：

```java
runtime.closeAsync()
        .toCompletableFuture()
        .get(30, TimeUnit.SECONDS);
```

**停机卡住时采样挂起操作**：

`closeAsync()` 的语义保持不变——无界等待排空收敛，框架不会注入隐藏超时，也不会因为读取诊断而跳过任何资源释放。有界等待超时后，应分别向各 owner 请求挂起操作快照并渲染，把“还在等什么”变成日志里的稳定文本：

```java
try {
    runtime.closeAsync().toCompletableFuture().get(30, TimeUnit.SECONDS);
} catch (TimeoutException stillPending) {
    System.err.println(runtime.advanced().pendingOperations().render());
    System.err.println(bus.pendingOperations().render());      // knotra-events
    System.err.println(adapter.pendingOperations().render());  // knotra-pf4j
    System.err.println(loader.pendingOperations().render());   // knotra-loader
}
```

四份快照彼此独立、各自 point-in-time，没有跨 owner 的全局聚合视图；空列表只代表采样瞬间没有已知挂起操作，不能证明 close 已经完成。诊断用于解释等待原因，不要从诊断推断 close 完成，完成与否只以 close future 的收敛为准。

跨层定位时用稳定 ID 关联同一条阻塞链。例如一个插件监听器卡住了事件分发，进而阻塞组件销毁与 artifact 卸载：

```text
# adapter.pendingOperations().render()
closeRequested=true
ARTIFACT_DRAIN|pricing-plugin|COMPONENT|PT2.134S|phase=dispose-roots, rootIds=[m-42], closureIds=[pricing-plugin]
omitted=0

# runtime.advanced().pendingOperations().render()
closeRequested=true
COMPONENT_TRANSITION|m-42|COMPONENT|PT2.134S|component dispose
LIFECYCLE_CLEANUP|entry-17|LIFECYCLE_ENTRY|PT1.921S|async pricing-listener
omitted=0

# bus.pendingOperations().render()
closeRequested=false
EVENT_DISPATCH|event-dispatch-bus-3-12|LISTENER|PT2.301S|event=OrderCreated type=com.demo.OrderCreated mode=SERIAL listeners=1
EVENT_SUBSCRIPTION_DRAIN|event-subscription-bus-3-8|DISPATCH|PT2.301S|pending dispatches=1 ids=[event-dispatch-bus-3-12]
omitted=0
```

关联方式：adapter 侧 `rootIds` 中的 `m-42` 与 core 侧 `COMPONENT_TRANSITION` 的 targetId 是同一个挂载句柄；该句柄的 `LIFECYCLE_CLEANUP` 条目说明正在清理 `pricing-listener`；事件侧被卡住的 `EVENT_DISPATCH` targetId 又出现在 `EVENT_SUBSCRIPTION_DRAIN` 的 `ids=[...]` 中。沿这条链即可从“插件卸载慢”定位到具体卡住的监听器回调。

## 线程上下文类加载器（TCCL）规则

在混合使用 Spring、ServiceLoader、Jackson 等框架时，框架通常会通过 `Thread.currentThread().getContextClassLoader()` 读取 TCCL。

Knotra 在生命周期边界（如组件启动、清理）会自动设置正确的类加载器，并在 `finally` 块中精确恢复。

业务代码开发需遵守：
1. **禁止在业务逻辑中随意篡改 TCCL** 而不恢复。
2. **线程池隔离**：提交给共享线程池的任务不得隐式捕获插件私有的 ClassLoader。
3. **Spring 模块指定 Loader**：使用 `SpringModules` 挂载插件配置类时，显式传入插件专属的 `ClassLoader`。

## 动态调用租约（Lease）机制

### 1. 方法级租约
使用 `Beans.dynamic(...)` 注入的接口代理，其生命周期如下：
* 每次方法被调用前，代理自动获取当前最新提供方实例的一个短暂租约。
* 方法执行完毕后，租约立即释放。
* 在方法执行期间，即使后台发生了策略热替换，当前执行中的方法依然能够安全完成，不会发生中途突变。

### 2. 跨方法显式租约
如果多个步骤必须观察完全相同的提供方版本：

```java
DynamicCapability<Pricing> pricing = context.subscribe(Pricing.class);

Quote quote = pricing.call(current -> new Quote(
        current.calculatePrice(orderId),
        current.calculateDiscount(orderId)));
```

对于响应式或异步链路，使用 `pricing.callAsync(...)`，租约会自动保持有效，直至返回的 `CompletionStage` 最终完成。在途排空机制会等待所有租约释放后再行销毁旧组件。

## 确定性资源释放（LIFO）

在组件生命周期中创建的任何需要关闭的资源（连接池、通道、文件句柄），必须统一登记到 `context.lifecycle()` 中：

```java
// 同步资源托管（按 LIFO 逆序释放）
DataSource dataSource = createDataSource(config);
context.lifecycle().manage("data-source", dataSource);

// 异步资源托管
HttpClient client = HttpClient.create(config);
context.lifecycle().manageAsync("http-client", client);

// 自定义清理钩子
context.lifecycle().onClose("cache-cleaner", () -> cache.clear());
```

**逆序释放保证**：如果组件 A 在启动时先初始化了数据源，再启动了消费线程，销毁时 Knotra 会严格保证先关闭消费线程，再关闭数据源，避免产生数据写入异常。

## 生产优雅停机六步法

在容器化（K8s / Spring Boot）生产环境中，推荐的优雅停机顺序如下：

```mermaid
graph LR
    A["1. LB/网关摘流"] --> B["2. 业务在途排空"]
    B --> C["3. 关闭 Loader & Adapter"]
    C --> D["4. 关闭宿主挂载点"]
    D --> E["5. runtime.closeAsync"]
    E --> F["6. 诊断检查与重试"]
```

```java
// 1. 网关停止分发新流量并等待在途业务请求完成
gateway.stopTraffic();
gateway.drain(Duration.ofSeconds(30));

// 2. 关闭 Loader 与插件适配器（排空插件调用）
loader.closeAsync().toCompletableFuture().get(30, TimeUnit.SECONDS);
adapter.closeAsync().toCompletableFuture().get(30, TimeUnit.SECONDS);

// 3. 关闭运行时内核
runtime.closeAsync().toCompletableFuture().get(30, TimeUnit.SECONDS);
```

第 6 步若发现有界等待未收敛，按上文“停机卡住时采样挂起操作”分别采样 runtime、事件总线、适配器与 Loader 的挂起快照后再决定重试或告警。
若出现清理失败，Knotra 将保留 `FAILED` 状态与诊断详情，允许显式发起 `retryAsync()`，绝不伪造虚假的“关闭成功”。

## 监控指标与告警建议

可以通过 `runtime.advanced().snapshot()` 采集纯数据指标并对接到 Micrometer / Prometheus：

```java
// 1. 活跃挂载点数
Gauge.builder("knotra.mounts.active", () ->
        runtime.advanced().snapshot().mounts().stream()
                .filter(m -> m.state() == ComponentState.ACTIVE).count())
        .register(registry);

// 2. 失败挂载点数
Gauge.builder("knotra.mounts.failed", () ->
        runtime.advanced().snapshot().mounts().stream()
                .filter(m -> m.state() == ComponentState.FAILED).count())
        .register(registry);

// 3. 注册项总数
Gauge.builder("knotra.registrations", () ->
        runtime.advanced().snapshot().registrations().size())
        .register(registry);
```

### 推荐告警规则
* `knotra.mounts.failed > 0` 持续超过 1 分钟：提示有组件激活或清理失败。
* 动态代理调用抛出 `MissingProvider` 频次异常升高：提示所需服务未就绪。
* 单次 `awaitSettled(...)` 耗时超过预期阈值：提示存在耗时较长的在途请求或阻塞操作。

## 生产超时预算推荐表

| 操作类型 | 建议超时预算 | 说明 |
|---|---|---|
| 本地 POJO Bean 激活 | 5 - 10 秒 | 仅涉及本地构造与依赖组装。 |
| 外部连接型组件激活 | 10 - 30 秒 | 涉及数据库连接池、网络握手。 |
| 动态策略热替换收敛 | 5 - 15 秒 | 依赖动态代理时通常可在毫秒级收敛。 |
| 插件在途排空（Drain） | 30 - 60 秒 | 等待已有业务请求平滑处理完成。 |
| 运行时整体停机（Close） | 30 - 60 秒 | 确保所有 LIFO 资源安全释放。 |
